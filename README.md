# Remember me

给 AI 一份不改写的对话档案，和一条能回答"那是哪一年、持续了多久"的时间轴。

原文一字不改地存，判定与检索路径 **0 次模型调用**，纯 Python 标准库，无第三方依赖。

> **English TL;DR** — A long-term memory engine for AI companions. It stores every user
> utterance **verbatim** and never summarizes. Importance is decided by closed word lists
> and arousal cues, not by an LLM, so the abstraction path makes **0 model calls** and
> cannot drift the way repeated summarization can. Retrieval returns a **time-axis
> cross-section**, which lets the model answer *"what happened that year"* and *"how long
> did it last"*. Pure Python stdlib, ~2.3k lines (300 of them are word lists), no GPU, no
> embedding, no network. **Unreviewed v0.9 hobby project — all numbers below are the
> author's own measurements on self-built corpora, not a benchmark.**

---

## 它想解决什么

长期陪伴的对话会持续几个月到几年。三个现实问题：

1. **上下文窗口放不下。** 把全部历史塞进去，成本和延迟都不可接受。
2. **滑动窗口会忘。** 只留最近 N 条，三个月前说的事就没了——而恰恰是那件事重要。
3. **让模型摘要会改口。** 摘要是模型写的，下一轮它可能把摘要里的措辞当成用户的原话；
   多轮摘要还会层层累积误差。

第三条是这个项目最主要的动机。所以这里的做法是：**不做摘要，原文进、原文出。**

代价写在这：判得没那么聪明。判定器认的是词表和规则，认不出的就不认（见「已知边界」第 1 条）。

## 三条设计约束

1. **原文不可改。** 除了把换行压成空格、去掉首尾空白，写进去和读出来的是同一句话。
   库里没有任何摘要，也没有任何一句是生成的——落盘的字段只有 `d/text/pin/score/ch/kinds` 六个，
   其中没有一个来自模型。
2. **抽象路径上 0 次模型调用。** 判定和取关键词全部是封闭词表 + 纯规则。
   规则会判错，但规则不会漂移——同样的输入永远是同样的判定。
3. **"遗忘"不删字节。** 不重要的句子不进常驻层（`spine`）、在检索里排后面，
   但原文仍然完整躺在磁盘上。`events.jsonl` 只有两处会写：`add()` 追加，
   和 `rejudge` 按新判定器原地重算（重写前先备份，写到临时文件再 `os.replace`）。

## 为什么要有"轴"

只存句子，能回答"我说过什么"；存了日期并按时间排开，才能回答另外两个问题：

```
病    12次   跨 0.3 年   2021-03-16 → 2021-07-04
住处  18次   跨 4.7 年   2021-07-24 → 2026-04-08
```

「老陈的病拖了三个多月」「房子的事她纠结了四年七个月」——这类句子的答案不在任何一条记忆里，
而在两条记忆的日期之间。普通向量检索取的是"最相似的几条"，不顺手做时间聚合的话，
拿不到这个跨度。

人的记忆也大致是这样组织的：你记得的不只是"我妈住过院"，还有"那是从三月开始的，拖到了夏天"。

```
    心里       6次  跨  4.0 年   2021-03-16 → 2025-03-18
    生死       2次  跨  3.8 年   2021-12-19 → 2025-10-06
    住处       3次  跨  1.4 年   2024-11-30 → 2026-04-08
```

**贴完这段得说两句实话，不然就是在挑好看的截图：**

1. 问「老陈是怎么走的」，最该被取出的那句——`五点二十，他走了。我一直握着他的手，握到天亮`——
   **这次没被取到**。因为它通篇用「他」，不含「老陈」，字面检索找不到它。
   它确实在库里、也确实在常驻刻度层里（demo 后半段能看到），但不指望这种方式命中代词句。
   这是「已知边界」第 2 条。
2. 第二个问题「我养过狗吗」，库里没有狗，它**返回空**，而不是返回「猫」让模型自由发挥。
   召回为空时输出的是一句固定文本，**没素材可编**——这比在提示词里反复叮嘱"不要编"更实在。
3. 上面「涉及：住处」也是不准确的——这次取到的四句里三句在讲房子，类别就按它们统计了。
   类别是从命中的句子现算的，不是对问题的理解。

## 安装

纯 Python 标准库，**没有任何依赖**。Python 3.8+。

```bash
git clone https://github.com/<你的用户名>/Remember-me-skill.git
cd Remember-me-skill
python run.py selftest        # 22 条不变量，全绿才算装好
```

作为 Agent Skill 使用时，把整个目录放进你的 skills 目录，**目录名用 `remember-me`**
（WorkBuddy：`~/.workbuddy/skills/remember-me/`；Claude Code：`~/.claude/skills/remember-me/`）。
目录名要和 `SKILL.md` 里的 `name` 一致，钩子的绝对路径也会指向它。

## 装好之后：不用再手动调用

**你不需要每轮都调它。** 挂一个钩子，之后正常聊天就行。

在 `~/.workbuddy/settings.json` 里加一段（`hooks` 的格式和 Claude Code 一致）：

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "\"<python 绝对路径>\" -S \"<skill 目录>/hooks/remember_hook.py\"",
            "timeout": 20,
            "statusMessage": "记住这句话"
          }
        ]
      }
    ]
  }
}
```

改完**要完全退出 WorkBuddy 再打开**（右键托盘图标退出，或任务管理器结束所有 `WorkBuddy.exe`）。
只关窗口不算——引擎会在启动时对钩子配置做快照，daemon 还活着的话仍用旧配置。

之后会发生三件事：

| 场景 | 它做什么 |
|---|---|
| 你随便说一句（"今天下雨了"、"我妈住院了"） | 存进库，**不占上下文** |
| 你问"你还记得…""上次…""那年…""什么时候…" | 自动把相关记忆贴进上下文（常驻层 + 相关句），模型于是想起来了 |
| 你说"/clear"、粘贴的 `<系统消息>` | 跳过，不入库 |
| 你让我改代码、贴报错 | **照样入库**，只是判定器不会把它标成刻度 |

> 最后一行是实话：钩子只按"斜杠命令 / 已知前缀 / 纯追问 / 重复句"这几条跳过，
> **不做"这是不是代码任务"的语义判断**——那需要模型，而这里全程 0 次调用。
> 嫌工作对话脏了人生记忆，就在那个目录放 `.remember-me-disable`，
> 或者把代码项目单独放一个目录。

看不懂它在不在工作？看 `~/.remember-me/hook.log`，每一轮都会留一行：

```
2026-10-27 15:33:01  OK 存=18字 注入=0字 耗时=33ms | 今天下雨了路上好堵
2026-10-27 15:33:20  OK 存=14字 注入=1426字 耗时=41ms | 你还记得我妈身体怎么样吗
```

没有新行 = 钩子没被触发，多半是没完全退出重开。

三种关法：

- **全局**：从 `settings.json` 删掉 `hooks.UserPromptSubmit` 这一段
- **单个目录**：在该目录下建一个空文件 `.remember-me-disable`（适合放代码项目，免得工作对话混进人生记忆）
- **临时**：环境变量 `REMEMBER_ME_HOOK=off`

> 为什么"存"和"提"要分开：每轮都注入会撑满上下文，而且十句话里有九句（"帮我改个 bug"）跟人生记忆无关。
> 琐事照样入库，只是不主动提。
>
> **`-S` 别省**：钩子每条消息都要新起一个 Python 进程，而 Python 启动时会扫 `site-packages`。
> 本机实测（同一台机器、同一份脚本、P50）：
>
> | | 默认 | 加 `-S` |
> |---|---|---|
> | 直接 exec | 488 ms | **293 ms** |
> | 经 shell | 708 ms | **447 ms** |
>
> 钩子只用标准库，`-S` 跳过 site 完全安全，省 40%。**别用 `-I`** —— 它隐含 `-E`，
> 会忽略 `PYTHONIOENCODING`，中文日志立刻变乱码（实测过）。
>
> **输出的格式是硬要求**：`UserPromptSubmit` 的 stdout 不是裸文本，宿主只认
> `{"hookSpecificOutput": {"hookEventName": "UserPromptSubmit", "additionalContext": "..."}}`。
> 直接 print 一段文字，宿主解析不出来，等于白跑一轮 —— 我第一版就是这么写的。
>
> 换到别的宿主（Claude Code / 其他 Agent 框架）时，把 `hooks/remember_hook.py` 挂到它对应的
> "用户提交前"事件上即可——它就是一个读 stdin JSON、往 stdout 打印 JSON 的普通进程。

## 用法

```bash
python run.py init                              # 建库（默认 ~/.remember-me）
python run.py add "我妈住院了"                    # 存一句原话
python run.py add "今天下雨了" --date 2024-03-05  # 补历史
python run.py ingest chat.tsv                   # 批量：日期<TAB>原话
python run.py recall "我妈身体怎么样"             # 取横截面（贴进上下文）
python run.py axis                              # 看人生轴
python run.py milestone                         # 看刻度（库里最重的那几十句）
python run.py stats                             # 看统计
python run.py rejudge                           # 判定器升级后重算全库（先 --dry-run 看一眼）
python run.py report                            # 读 hook.log，报真实的读写与注入开销
```

### 库放在哪、ingest 吃什么

默认库目录是 `~/.remember-me`。三种改法，优先级从高到低：

- 命令行 `--home`：`python run.py --home D:\mem stats`（放命令前后都行）
- 钩子读环境变量 `REMEMBER_ME_HOME`
- 代码里 `Store(path)`

`ingest` 每行三种形态，按这一行的列数自动认：

| 行 | 结果 |
|---|---|
| `2024-03-05<TAB>我妈住院了` | 用行首日期 |
| `2024-03-05<TAB>我<TAB>我妈住院了` | 第二列**被丢弃**（那是导出文件里的角色名），第三列起合并为正文 |
| `我妈住院了` | 用今天日期 |

行首那 10 个字符不是合法日期时，整行当正文，日期取今天。

### 接进任何模型（三步）

```python
from engine.store import Store
from engine import axis

st = Store("~/.remember-me")

for line in user_turns:                     # ① 每轮都存，不调模型
    st.add(line)

block = axis.render(st.load(), question, idx=st.index())   # ② 取这次要的那几句
messages = [                                                 # ③ 贴进上下文
    {"role": "system", "content": SYSTEM_PROMPT + "\n\n" + block},
    *history,
    {"role": "user", "content": question},
]
```

`recall` / `render` 的输出已经是可直接粘贴的格式，带日期、带 ★ 刻度标记、带类别提示
（`（涉及：生死、病、住处）`）。**它不绑定任何模型厂商**——因为它只是一段文本。

## 作者自测

分三类：**可一键复现的**、**内部实验（不是 benchmark）**、**没验证的**。

### 一、可复现：自检与规模基准

```bash
python run.py selftest     # 22 条不变量，当前 22/22
python hooks/_selftest.py  # 钩子 9 条，当前 9/9
python bench_scale.py      # 现场造 1万/5万/20万条并计时，不读历史结果
```

自检测的是**逻辑不变量**，不是效果：比如"检索不改变存储（前后字节一致）"、
"长文不能因为长就被判成重要"、"没有相关记忆时必须返回空"、"金标 99 条上 P≥0.95 / R≥0.90"。
这些都是确定性断言，改动代码后跑一遍就知道有没有搞坏。

**环境**：Windows / Python 3.13 / 单进程 / 本机 SSD，都没开多线程。
下面所有毫秒数换台机器就会变，别当承诺。

### 二、写入与存储

| | 数字 | 怎么来的 |
|---|---|---|
| 单条写入（追加一行） | P50 0.26ms / P95 0.36ms | `bench_scale.py`，每 50 条 `fsync` 一次 |
| 单条开销 | 85 ~ 151 字节（短句 / 长句） | 实测 jsonl 行宽 |
| 十年密集陪伴（36.5 万条） | 31 ~ 55 MB | **按单条均值线性外推，没真跑十年** |
| 五十年（182 万条） | 155 ~ 275 MB | 同上 |

> `fsync` 那个数字是**基准脚本的条件**，不是产品行为：`add()` 默认 `sync=False`，只 flush 不 fsync
> （每条都 fsync 会把写入拖到几毫秒）。要每次落盘就对 `add(..., sync=True)`。

为什么敢存原文：太贵的东西才需要压缩。一条短句一百来字节，压缩省下的那点空间，
不值得用"改写用户的话"去换。

### 三、读取延迟

本机连跑三次，下表取中位数（括号里是三次的范围）。**换个机器、换个磁盘，这些数字都会变。**

| 规模 | 冷启动 load | 热启动 load | 召回 P50 | 召回 P95 |
|---|---|---|---|---|
| 1 万条 | 203ms（146~413） | 14ms（11~57） | 5ms（4.9~7.3） | 20ms（7.7~21.5） |
| 5 万条 | 866ms（715~1038） | 85ms（60~96） | 18ms（16~18） | 44ms（41~54） |
| 20 万条 | **3.8s**（3.4~4.1） | **437ms**（290~518） | **57ms**（44~76） | **245ms**（189~284） |

三个优化，方向是确定的（具体倍数每次测都不一样）：
- 写入时定型事件类型，读时不再跑正则 → 冷启动省一半左右
- pickle 缓存 + `(mtime, size)` 签名 → 热启动从秒级降到几百毫秒
- 内存倒排索引，只对候选集打分 → 20 万条召回从几百毫秒降到几十毫秒

> 同一台机器、同一份脚本，三次跑出来的差异能到 1 倍以上。表里报中位数，别把任何一个数当承诺。

### 四、内部对照实验（**不是 benchmark，别当结论引用**）

做法：让 6 个 AI 模型各扮一个人设（年龄、家庭状况各不相同，彼此不知道判定规则），
各写一份五年跨度的对话日志，合计 3125 句。其中 4 个人设做了 A/B：
同一个问题问两遍，一遍只给最近 40 条（模拟常见的滑动窗口），一遍给记忆轴。

| 人设 | 只给最近 40 条 | 给记忆轴 |
|---|---|---|
| 19 岁大学生（奶奶阿尔茨海默） | 9.9% | 33.0% |
| 45 岁小超市老板（父亲肺癌） | 9.0% | 23.7% |
| 62 岁丧偶教师 | 5.9% | 54.7% |
| 33 岁离婚程序员 | 8.8% | 32.8% |
| 均值 | 8.4% | 36.1% |

指标是"答案覆盖了多少真值要点"（ROUGE-2 recall 的近似），不是人工打的满意度分。

**这个实验有四个明确的缺陷，我按严重程度列：**

1. **语料不是真人写的。** 六个人设由模型扮演，用词和叙事节奏有共性。真实用户的分布一定更杂，
   这个数字到真实场景大概率会掉，掉多少我不知道。
2. **只有 4 个人设。** 4 个样本说不了统计显著性，"四个人设都同向"只能算一个观察。
3. **判分口径是我自己定的，而且改过三次。** 其中一次因为日期格式差异，把 52 条正常回答误报成"编造"。
   最终口径比以前稳，但仍然是作者的主观选择。
4. **方差大。** 同一份 prompt 跑三次得到 78.3% / 76.4% / 89.6%（这是另一个 12 题探针的覆盖率口径）。

**所以：方向（有轴的比只有滑窗的好）我认为可信；具体百分数不可信，不要引用。**

62 岁那位另用一套手写锚点逐题读过：26.4% → 96.4%，编造 0~1 条。这个是手写标准、我一个人评的，
主观性比上面更强，只作为参考。

### 五、没有验证的部分

诚实清单：

- **没在真实用户身上长期跑过。** 连续使用时间最长的记录是几周，不是几年。
  "十年后还记得"是设计目标，不是已验证的结果。
- **没和别的记忆方案做过同条件对比。** 上面的基线是"最近 40 条"这个朴素做法，
  就是"最近 40 条"本身。跟任何真实产品的成绩都不是同一个条件，拿它去比较是不公平的。
- **只测过中文。** 词表、停用词、委婉语分级全部基于中文，英文需要重建整套词表。
- **没测过并发和多用户。** 单进程、单库、单用户。多开进程写同一个库可能出问题。
- **判定器的准确率只在自建金标上测过。** 99 条是我自己标的，有偏。

## 已知边界

写在前面：这些是踩出来的，不是猜的。

**1. 纯叙述型的重要时刻判不出来。**

> 「考完了，最后一道大题没写完，我走出考场的时候腿是软的，我完了」

没有一个事件词。人在最要紧的时刻，**反而不说事件名**。
只用词表判重要性，在自建的 3125 句语料上 P=35.5% / R=27.6%，加三轮规则只涨 0.9 个点。

**这也是为什么判定器不负责删任何东西，只负责打刻度。** 它判错的代价是"刻度不准"，不是"记忆丢失"。

**2. 代词会切断实体线。** 「五点二十，他走了」不含人名。靠常驻刻度层兜底，没有真正的指代消解。

**3. 问句和原文用词不一致时会漏。** 问「为什么从加拿大回来」，讲原因那句里没有"加拿大"。
（已加"问法别名表"和"实体首末时间窗"缓解，未根治。）

**4. 高频实体的覆盖不全。** 一个被提了 90 次的人，单次检索只取其中一部分。

**5. 只有中文。**

## 设计上的取舍

这几条说的是**代码里确实这么写了**（可以对着源码核），不是"所以我们更好"。

| 取舍 | 代码里的表现 | 换来什么 / 付出什么 |
|---|---|---|
| **库里没有一句是模型写的** | 一条记录就是六个字段（`d/text/pin/score/ch/kinds`），`text` 只由 `add()` 从入参写入，全链路没有生成环节 | 换来：不存在"摘要被当成用户原话"这条路径（自检 A5 会验证注入的每一句都在库里）。付出：做不了任何需要概括的整理 |
| **抽象路径 0 次模型调用** | 判定和类型全在 `engine/judge.py`，封闭词表 + 正则 | 换来：判定可复现，改一版词表跑一次 `rejudge` 就能全库重算。付出：判得笨，纯叙述型的重要时刻会漏（见边界 1） |
| **能给出时间跨度** | `milestones()` 把同类刻度的首末日期相减（`DAYS_PER_YEAR` 换算） | 换来：能答"持续了多久"。付出：依赖日期准确，导入历史数据时日期填错就全错；只对**反复发生**的类型有跨度 |
| **召回不写记忆库** | `retrieve()` 不碰 `recs`，自检 I9 比对 `events.jsonl` 的字节 | 换来："你问过什么"不会改变"你是什么"。付出：没有基于反馈的自动调优 |
| **遗忘不删字节** | 不重要的句子权重低、进不了 `spine()`，但那一行 jsonl 不动 | 换来：不会丢数据。付出：磁盘不会因此变小；隐私上不能靠"遗忘"解决 |

一组上限（都是代码里的常量，可以直接对着源码核）：

| | 上限 | 出处 |
|---|---|---|
| 单次召回 | **26 句**（`budget=20`，截断时放宽 6 句） | `engine/axis.py` `retrieve()` |
| 常驻刻度层 | **64 句**，单条 ≤120 字 | `spine(cap=64)` / `SPINE_MAX_CHARS` |
| 钩子注入（两者合并） | 理论上限 90 句 | `render(with_spine=True)` |

库里 600 句还是 50 万句，这一块都一样大——这是"上下文长度"这个约束在这里的处理方式：
不把库塞进去，每次只取这次要的那几句。实测一个五年、64 句的库，钩子一次注入约 20 句 / 2~4KB。

如果你要的是"用 LLM 把对话总结一下存起来"，那这个项目不是。它全链路一次模型都不调用，
代价已经写在上面了。

## 数据来源

关键事件词表不是全手编的，来自可核查的公开来源：

- **张明园《生活事件量表》(LES) 48 项 (1987)** — 事件词骨架。五个公开来源交叉核对，条目一致。
- **中文死亡委婉语分级表**（维基词典 / 中国新闻网 / 新华网）— A 级直判（去世/病逝/出殡）、
  B 级需近亲主体（"奶奶走了"是、"同事走了"不是）、C 级不收。
- **SUBTLEX-CH** (Cai & Brysbaert 2010, PLOS ONE) — 仅用于过滤零频次词与关键词排序。
  > 注意：它是**翻译过来的电影字幕**，中频段是"吸血鬼/凶手/陪审团"，而"腰疼""生孩子""领证"频次全是 0。
  > **不适合拿来裁生活词**，我试过，会把最该记的词删掉。
- **哈工大 + 百度 + 四川大学停用词表** — 关键词过滤。

感谢上述项目的作者。

## 不做什么

- 不联网、不用 embedding、不用向量库、不用 GPU
- 不调用模型（判定、聚簇、取关键词全部纯规则）
- 不生成摘要、不改写原话
- 不在召回时写入任何东西（检索零写入，有断言保证）
- 没有删除接口。想"忘掉"只能降检索优先级，不能删字节
- **不存密码、密钥、令牌、银行卡号。** 库是明文 `events.jsonl`，方便你 `tail`、`grep`、备份，
  方便到"打开就能读"。别把不该落盘的东西说给它听；说了就写入磁盘了，本引擎没有加密层
